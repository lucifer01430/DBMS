Section 04

Introduction

✎ Simple Definition

The Entity Relationship Model is a high-level data model used to describe real-world objects, their properties, and the relationships between them before converting the design into tables.

ER modeling is the bridge between a real problem and a database design. When someone says, "Build a database for a college library," you should not immediately create tables. First, you identify the important objects: Student, Book, Librarian, Issue Record, and Fine. Then you identify what each object needs to remember and how the objects are connected.

What?

A visual model of entities, attributes, relationships, constraints, and keys.

Why?

To understand the real-world problem before tables are created.

How?

Convert nouns into entities, properties into attributes, and actions into relationships.

Where used?

College systems, banking systems, hospital systems, railway booking, e-commerce, and inventory systems.

Section 05

Why This Topic Exists

⚡ Real Problem

Users describe systems in ordinary language, but databases need precise structure. ER modeling exists because jumping directly from spoken requirements to tables often creates missing entities, repeated columns, weak keys, and unclear relationships.

Step 1 Requirement

"A student can issue many books."

->
Step 2 ER Thinking

Student and Book are entities; Issue is the relationship.

->
Step 3 Design Decision

The relationship has dates, so it may later become its own table.

Real-World Analogy

An ER diagram is like an architect's floor plan. Nobody starts building a house by randomly placing walls. First, the architect draws rooms, doors, connections, and constraints. Similarly, a database designer draws entities, relationships, keys, and constraints before building tables.

Exam Perspective

When asked "Why ER model?", write that it provides a high-level conceptual design and communicates requirements clearly before implementation.

Interview Perspective

Say ER modeling prevents poor schema design by forcing the designer to understand objects, relationships, and rules first.

Section 06

ER Model Concepts

The ER model is built from a few core concepts. Once these are clear, ER diagrams become predictable instead of confusing.

Entity

A real-world object that can be identified separately, such as Student, Book, Course, Account, or Doctor.

Entity Set

A collection of similar entities. All students together form the Student entity set.

Attribute

A property of an entity. Student may have RollNo, Name, Email, and Semester.

Relationship

An association between entities. Student borrows Book is a relationship.

Concept Map: ER Model Building Blocks

Fig 2.2 - The ER model is made from entities, attributes, relationships, and constraints

Step-by-Step Identification

  1. Read the requirement carefully. Underline nouns and important actions.
  2. Choose entities. Stable objects usually become entities: Student, Book, Course.
  3. Choose attributes. Details about an entity become attributes: Name, RollNo, Title.
  4. Choose relationships. Actions connecting entities become relationships: Enrolls, Borrows, Teaches.
  5. Choose constraints and keys. Decide how many objects can participate and how each object is uniquely identified.

Section 08

Mapping Constraints

Mapping constraints describe how many entities from one entity set can be associated with entities from another entity set. In exams, this is usually asked through examples.

One-to-One (1:1)

One person has one passport, and one passport belongs to one person.

One-to-Many (1:N)

One department has many employees, but each employee belongs to one department.

Many-to-One (N:1)

Many students are guided by one teacher, but each student has one guide.

Many-to-Many (M:N)

Many students enroll in many courses. A student can take many courses; a course can have many students.

Section 09

Keys

✎ Simple Definition

A key is an attribute or a set of attributes that helps identify an entity uniquely inside an entity set.

Without keys, the database cannot reliably tell two similar entities apart. If two students have the same name, "Name" cannot identify a student uniquely. But RollNo or UniversityRollNo may identify each student separately.

StudentRollNoNameEmailCan it identify uniquely?
S1101Amanaman101@mail.comRollNo and Email can work
S2102Amanaman102@mail.comName cannot work alone
S3103Nehaneha103@mail.comRollNo and Email can work
Small SQL-style idea...
-- Keys are design decisions before table creation.
CREATE TABLE Student (
  RollNo INT,
  Name VARCHAR(40),
  Email VARCHAR(60)
);
KEY

Key thinking starts in ER design. SQL enforces the decision later, but the designer must first understand which attributes can identify an entity.

Section 10

Super Key

A super key is any attribute set that can uniquely identify an entity. It may contain extra attributes that are not necessary for uniqueness.

💡 Real-Life Analogy

If RollNo alone identifies a student, then RollNo + Name also identifies the student. But Name is extra information. That larger combination is still a super key, but it is not minimal.

Example: Student Entity

Attribute SetUnique?Super Key?Reason
{RollNo}YesYesEach RollNo belongs to one student
{Email}YesYesEach email is unique
{RollNo, Name}YesYesRollNo already identifies; Name is extra
{Name}NoNoTwo students can have the same name

Section 11

Candidate Key

A candidate key is a minimal super key. It uniquely identifies an entity and does not contain any unnecessary attribute.

✎ Simple Test

First ask: does this attribute set identify uniquely? If yes, remove one attribute and test again. If removing any attribute breaks uniqueness, it is a candidate key.

Attribute SetSuper Key?Candidate Key?
{RollNo}YesYes, minimal
{Email}YesYes, minimal
{RollNo, Name}YesNo, Name is extra
{Name}NoNo, not unique

Section 12

Important Terminologies

Mini-World

The part of the real world being modeled, such as a library, hospital, or college system.

Entity Type

The structure or category of similar entities, such as Student or Book.

Entity Instance

One actual object inside an entity set, such as student RollNo 101.

Attribute Domain

The valid set of values an attribute can take, such as Semester from 1 to 8.

Relationship Set

A collection of similar relationships between entity sets.

Mapping Constraint

A rule that describes how many entities can participate in a relationship.

Super Key

Any attribute set that uniquely identifies an entity.

Candidate Key

A minimal super key with no unnecessary attribute.

Section 13

Key Points

  • ER model is a high-level conceptual data model used before table design.
  • Entities are real-world objects; attributes are their properties; relationships connect entities.
  • ER diagrams use standard notation: rectangles, diamonds, ovals, lines, and underlined key attributes.
  • Mapping constraints describe relationship cardinality: 1:1, 1:N, N:1, and M:N.
  • A key identifies an entity uniquely.
  • A super key may contain extra attributes; a candidate key is minimal.
  • Every candidate key is a super key, but every super key is not a candidate key.

Section 15

Common Mistakes

Treating every noun as an entity

Some nouns are attributes. "Student name" is usually an attribute, not a separate entity.

Using vague relationship names

Use meaningful verbs such as Borrows, Enrolls, Teaches, or Issues instead of generic names like "has".

Confusing super key and candidate key

Super key only needs uniqueness. Candidate key needs uniqueness plus minimality.

Forgetting mapping constraints

An ER diagram without cardinality information is incomplete for many exam questions.

Choosing Name as a key

Names are often repeated. Use attributes that are guaranteed unique in the problem context.

Drawing decorative diagrams

ER diagrams must communicate meaning, not decoration. Keep shapes standard and readable.

Section 16

Best Practices

  1. Start from requirements. Do not invent entities before reading the scenario.
  2. Name entities as nouns. Student, Book, Course, Account, Doctor.
  3. Name relationships as verbs. Borrows, Enrolls, Teaches, Owns.
  4. Underline key attributes clearly. This is important in hand-drawn exam diagrams.
  5. Check cardinality with real examples. Ask how many objects can connect on each side.
  6. Keep the diagram readable. A clean diagram with correct meaning is better than an overcrowded diagram.
Section 17

Memory Tricks

💡 Trick 1 - ER Basics

"Nouns become entities, details become attributes, verbs become relationships."

💡 Trick 2 - Candidate Key

"Candidate = Can identify + Cannot reduce." It must identify uniquely and remain minimal.

💡 Trick 3 - Mapping Constraints

"Count both sides." Ask how many entities on the left can connect to how many on the right.

Section 20

Chapter Summary

ER modeling is the conceptual design step that converts real-world requirements into a clear visual structure. The ER model uses entities, attributes, relationships, constraints, and keys to describe the mini-world before tables are created. ER notation gives a standard way to draw this design, while mapping constraints explain how many entities can participate in a relationship. Keys make entity identification reliable. A super key uniquely identifies an entity, and a candidate key is a minimal super key. If you can identify these parts from a scenario, you can design cleaner databases later.

Section 24

Interview Fundamentals

Explain ER model in one minute

ER model is a conceptual design model that represents entities, attributes, relationships, constraints, and keys before creating tables.

Super key vs candidate key

A super key uniquely identifies an entity. A candidate key is a minimal super key with no extra attributes.

How do you find entities?

Read the requirement and identify stable real-world objects. Usually nouns such as Student, Book, Course, and Account become entities.

Why mapping constraints matter

They show how many entities can participate in a relationship and prevent incorrect relationship design.
